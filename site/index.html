Ein Agent schreibt Code und weiß in derselben Runde, ob er stimmt.

In QAL liegt Code nicht in Dateien, sondern als geprüfte Funktionsknoten in einem Speicher. Jeder Schreibvorgang wird sofort getypt, bewiesen, getestet und mit dem ganzen Programm neu verknüpft. Die Antwort kommt in unter einer halben Sekunde, als JSON.

type Acct = { id: Int, balance: Int }

  req n >= 1
  ens r.balance > a.balance
= Acct { id: a.id, balance: a.balance + n }

test deposit_adds =

Der Name

QAL steht für Query & Agent Language

Beide Hälften des Namens beschreiben, wie die Sprache arbeitet.

Q
Query

Code wird abgefragt, nicht durchsucht

Der Code liegt in einem Speicher statt in Dateien. Ein Agent fragt ihn ab: wer eine Funktion verwendet (qal_query), wie eine Definition aussieht (qal_view), wie sie sich verändert hat (qal_history). Jede Antwort ist strukturiertes JSON statt Text, den man erst auswerten muss.

A
Agent

Gebaut für den, der schreibt

Die Sprache ist für KI-Agenten entworfen, nicht für Menschen am Editor. Deshalb prüft jeder Schreibvorgang sofort alles, jeder Fehler hat einen Code, einen Pfad und einen Hinweis zur Behebung, und jede Wirkung nach außen muss ausdrücklich freigegeben werden.

Warum jetzt

Der nächste Schritt: Sprachen für die Zeit, in der Agenten schreiben

Alle verbreiteten Programmiersprachen wurden für Menschen am Editor entworfen. Inzwischen schreiben KI-Agenten einen wachsenden Teil des Codes. QAL setzt dort an, wo sich dadurch der Engpass verschoben hat.

Was sich geändert hat

Code zu erzeugen ist billig geworden

Ein Agent schreibt in Sekunden, wofür ein Mensch Stunden braucht. Die Menge an Code wächst schneller, als Menschen ihn lesen und prüfen können.

Wo der Engpass jetzt liegt

Teuer ist das Prüfen

Ob der Code stimmt, zeigt sich in heutigen Sprachen erst später: im Testlauf, im Review, im Betrieb. Ein Agent erfährt es oft gar nicht oder zu spät.

Was QAL daraus macht

Prüfen ist Teil des Schreibens

Jeder Schreibvorgang wird sofort getypt, bewiesen, getestet und mit dem Programm verknüpft. Vertrauen entsteht aus maschinell geprüften Garantien, nicht aus Hoffnung.

Worum es gehtSprachen für MenschenQAL, eine Sprache für Agenten
Wo Code liegtTextdateien, die man durchsuchtgeprüfte Knoten im Speicher, die man abfragt
FehlermeldungenText für MenschenJSON mit Code, Pfad und Hinweis zur Behebung
Testsein späterer, eigener Schrittlaufen bei jedem Schreiben mit, so weit die Änderung reicht
VerträgeKommentare oder Laufzeit-Assertsvom Z3-Beweiser beim Schreiben bewiesen
Nebenwirkungenunsichtbar im Codeim Typ deklariert und einzeln freigegeben
Unbemerkte Rückschrittefindet ein Mensch, wenn er Glück hatmeldet das Verhaltensgedächtnis in derselben Runde
KI-Aufrufe im Programmein ungeprüfter API-Aufrufein Effekt mit Budget, Aufzeichnung und deterministischen Tests
Mehrere AgentenKonflikte im VersionsverlaufRollen, Leases, Merge-Tor und signierte Geschichte

Unsere These: Je mehr Code Agenten schreiben, desto weniger kann Vertrauen davon kommen, dass ein Mensch jede Zeile liest. Es muss aus der Sprache selbst kommen. QAL ist um diesen Gedanken herum gebaut. Was davon heute gemessen ist und was noch nicht besser ist, steht weiter unten bei den Zahlen und den Grenzen.

Die eine Runde

Fünf Prüfungen, ein Aufruf

Andere Sprachen verteilen diese Schritte auf Compiler, Testlauf, Linter und Review. In QAL sind sie die Antwort auf jedes Schreiben. Der Agent muss nichts davon selbst anstoßen; ein separates qal_test oder qal_prove danach ist nicht nötig.

Typen und Effekte

Passt es?

Typprüfung, Vollständigkeit jedes match, und jede Funktion nennt, was sie darf: !io, !fs, !net, !db, !model.

Z3-Beweis

Gilt der Vertrag?

Jedes ens und das req jeder Funktion an jedem Aufruf. Ein widerlegter Vertrag wird nicht gespeichert, die Diagnose enthält ein Gegenbeispiel.

Tests

Bricht etwas?

Alle gespeicherten Tests, die die Änderung erreichen, auch über andere Funktionen hinweg.

Property-Tests

Und an den Rändern?

Jede definierte reine Funktion bei 0, ±1, leeren Werten und an den Grenzen ihres req; dazu die Typ-Invarianten.

Neu verknüpfen

Stimmt der Rest?

Alle abhängigen Definitionen bekommen neue Hashes und werden mitgeprüft.

+ E0807

Das Verhaltensgedächtnis: Frühere echte Programmläufe werden wiederholt. Ändert ein define ihre Ausgabe, meldet die Antwort genau diese Läufe, einmal, mit alter und neuer Ausgabe.

Selbst ausprobieren

Der echte Compiler, hier in deinem Browser

Der QAL-Compiler ist in QAL geschrieben und zu WebAssembly übersetzt. Genau dieses Modul, 444 KB, läuft jetzt auf deinem Rechner. Schreib Code oder nimm ein Beispiel: Die Antwort ist dieselbe, die ein Agent bekommt.

Compiler wird geladen …
Noch nicht geprüft

Sobald der Compiler geladen ist, wird geprüft, während du tippst.

Im Browser laufen Parser, Typprüfung, Effektprüfung und Vollständigkeit der match-Ausdrücke. Die Z3-Beweise, die Tests und der Speicher laufen im vollständigen Werkzeug qal.

01 · Sprache

Klein, streng, ohne Überraschungen

Alles ist ein Ausdruck. Es gibt kein null, keine Ausnahmen, keine impliziten Umwandlungen und keine Schleifen.

TypenInt (64 Bit), Float, Bool, Unit, Str, Bytes, List[T], Map[K, V] (nach Schlüssel geordnet), Option[T], Result[T, E] und Funktionstypen.
Records und VariantenEigene Typen als Record oder als Aufzählung mit Daten.type Shape = Circle(Int) | Rect(Int, Int) | Dot
GenericsGenerische Typen und Funktionen; die Typargumente werden beim Aufruf abgeleitet.fn swap[A, B](p: Pair[A, B]) -> Pair[B, A]
Vollständiges Pattern MatchingMuster mit Konstanten, Varianten, Records und Wächtern. Jedes match muss alle Fälle abdecken.
ClosuresAnonyme Funktionen, die ihre Umgebung einfangen. Werte sind unveränderlich; Funktionen sind Werte.map(xs, fn(x) => x * k)
Effekte im TypWer liest, schreibt oder ins Netz geht, sagt es: !io !fs !time !rand !net !db !model. Aufrufer erben die Vereinigung.
Effekt-PolymorphieEine Funktion nimmt die Effekte ihres Callbacks an; mit einem reinen Callback bleibt sie rein.fn each[T, !e](xs: List[T], f: fn(T) -> Unit !e) -> Unit !e
Rekursion statt SchleifenEin Aufruf in Endposition ist eine Schleife. Listen werden mit map, filter, fold und range verarbeitet.
Exakte Ganzzahlena * b / c rechnet mit 128-Bit-Zwischenergebnis exakt. Ein echter Überlauf und Division durch null brechen ab, statt falsch weiterzurechnen.
Platzhaltertodo() steht für einen noch fehlenden Rumpf beliebigen Typs; ausgeführt bricht er mit E0540 ab.
02 · Verifikation

Beweisen, testen, erinnern

Vier Netze, die bei jedem Schreiben laufen: Beweise, Tests, Property-Tests und das Verhaltensgedächtnis.

Verträgereq ist die Vorbedingung, ens die Nachbedingung, r das Ergebnis. Zur Laufzeit gelten sie immer.fn sqrt_floor(n: Int) -> Int req n >= 0 ens r * r <= n
Z3-BeweiseExakt für Int und Bool, mit den Verträgen der aufgerufenen Funktionen. Widerlegt: nicht gespeichert, mit Gegenbeispiel. Nicht beweisbar: unknown mit Grund, zur Laufzeit geprüft.
Betroffene TestsEin define führt jeden gespeicherten Test aus, der eine geänderte Funktion erreicht, auch über Umwege.
Randwert-Property-TestsJede definierte reine Funktion an 0, ±1, leeren Werten und den Grenzen ihres req. Eingaben werden gezielt so gebaut, dass sie die Vorbedingung erfüllen.
Generierte Property-Testsqal_test prüft jede reine Funktion mit ens an 100 Eingaben; ein Fehler kommt mit verkleinertem Gegenbeispiel.
Typ-InvariantenEine reine Funktion inv_T ist die Regel für Typ T. Jede Funktion, die ein T nimmt oder liefert, wird darauf geprüft, auch tief in Listen und Records.
Verhaltensgedächtnis (E0807)Frühere Programmläufe werden bei jedem define wiederholt, bis zu 64 in 2 s. Geänderte Ausgaben werden einmal gemeldet und sind danach die neue Grundlage.
Warnung bei ungetesteter ÄnderungErsetzt ein define eine Funktion ohne einen Test, warnt E0806: jede neue Regel soll im selben Schritt einen Test bekommen.
Gedächtnis für KorrekturenWurde ein Fehler früher schon behoben, nennt die neue Diagnose die damalige Lösung; qal_recall listet frühere Korrekturen.
Beweise nach HashErgebnisse werden pro Definition und Hash gespeichert. Was sich nicht geändert hat, wird nicht noch einmal bewiesen.
03 · Speicher

Code als adressierte Knoten

Ein SQLite-Speicher in .qal/store.db. Jede Definition steht dort unter dem SHA-256 ihrer kanonischen Form.

Nur Geprüftes wird gespeichertWas nicht parst oder nicht typt, kommt gar nicht in den Speicher. Jeder Fehler ist eine JSON-Diagnose mit Pfad und Hinweisen.
Ersetzen mit NeuverknüpfungEin bestehender Name wird ersetzt. Bei gleicher Signatur werden alle Verwender automatisch neu verknüpft und geprüft.
SignaturänderungenAbhängige, die weiter passen, ziehen mit; die anderen werden mit ihren Fehlern abgelehnt, außer derselbe Aufruf definiert sie neu.
Umbenennen ohne Neuschreibenqal_rename ändert keinen Hash; alle Verwender folgen dem neuen Namen.
Sicheres Löschenqal_delete entfernt nur, was niemand mehr verwendet.
AbfragenNach Name, Typ-Muster oder Verwendern; eine Übersicht mit Verträgen, Verwendern und Tests (--outline).
VerlaufJede Änderung jedes Namens mit altem und neuem Hash, Zeitpunkt und Agent.
Inkrementelles PrüfenGeprüft und gehasht wird nur, was sich ändert, und das Ergebnis ist byte-gleich mit der vollständigen Prüfung. Bei 1520 Definitionen sind es 0,43 statt 1,7 s.
PaketeTeile des Speichers lassen sich als .qalpkg exportieren, importieren und installieren, aus einer Datei oder von einer URL.
Mehrere SchreiberGleichzeitige Schreibvorgänge werden über eine Sperre hintereinander gereiht; ein Beweis läuft dabei außerhalb der Sperre.

06 · KI-Aufrufe

Modelle als budgetierter Effekt

Programme können selbst ein Sprachmodell fragen. Das ist ein Effekt wie jeder andere: deklariert, freigegeben und begrenzt.

std.modelask liefert Text, ask_full zusätzlich Modell, Tokens und Kosten, ask_json geparstes JSON nach einem Schema.
BudgetJeder Aufruf wird gegen ein festes Budget in Euro gebucht, aufgerundet. Ist es aufgebraucht, kommt ModelBudgetExceeded statt eines weiteren Aufrufs.
AufzeichnungJede Antwort wird nach Prompt, Schema und Modell gespeichert. Dieselbe Frage kostet beim zweiten Mal nichts.
Deterministisches Abspielen--replay spielt nur Aufgezeichnetes ab, ohne Netz und ohne Schlüssel. Tests dürfen ein Modell fragen und sehen immer nur aufgezeichnete Antworten.

09 · Team

Mehrere Agenten, klare Rollen

Ein Team-Speicher lässt mehrere Agenten zusammenarbeiten, mit Rollen, Änderungssätzen und einer lückenlos signierten Geschichte.

Vier RollenArchitektur legt Schnittstellen und Verträge fest, Implementierung füllt Rümpfe, Verifikation schreibt Tests und prüft, Review liest und gibt frei.
ÄnderungssätzeCode entsteht nur in eigenen Änderungssätzen; der Hauptstand ändert sich nur durch einen Merge.

Ein echter Fang

Alle Tests grün, und trotzdem ein Fehler

Ein Haiku-Agent sollte mehrzeilige Bestellungen einbauen. Nach seinem ersten define bestanden alle seine eigenen Tests. Nur das Verhaltensgedächtnis meldete, dass eine alte, einzeilige Bestellung jetzt anders kostet.

  1. Der Agent las die Warnung und erkannte: Einzeilige Bestellungen müssen gleich bleiben.
  2. Er korrigierte die Rabattformel in der nächsten Runde.
  3. Gegenprobe: Der Stand vor der Korrektur hätte 5 von 50 verborgenen Tests verletzt.

Bei gezielt eingebauten Fehlern meldet E0807 allein, ohne einen einzigen Test, 11 von 13. In 30 Live-Versuchen gab es keinen Fehlalarm.

E0807 behaviour_changed
this define changed what `main` prints on 3 of 25 earlier runs: `OK o1 8800` is now `OK o1 8835`
Wörtlich aus Versuch 12, Commit 9ab47ae8
Warum QAL

Wenn ein Agent den Code schreibt

  • Rückmeldung in einer RundeEin Agent erfährt sofort, ob Typen, Verträge, Tests und Abhängige stimmen. Er muss keinen Build-Lauf planen und keine Logs lesen.
  • Fehler, die Tests nicht sehenBeweise und das Verhaltensgedächtnis fangen, was die eigenen Tests eines Agenten übersehen.
  • Kontrollierte WirkungJeder Effekt steht im Typ und muss freigegeben werden. Ohne --allow model kann ein Programm kein Modell aufrufen und kein Geld ausgeben.
  • Antworten als DatenJedes Ergebnis ist JSON, jeder Fehler hat einen Code, einen Pfad und einen Hinweis zur Behebung.
  • Zusammenarbeit ohne ChaosRollen, Leases, ein Merge-Tor und eine signierte Geschichte machen nachvollziehbar, welcher Agent was geändert hat.
Was noch nicht besser ist

Ehrlich gemessen

  • KostenAgenten brauchen in QAL etwa 1,3-mal so viele Tokens wie in Rust. Der größte Posten ist die Sprachreferenz, die jeder Agent mitliest.
  • Kein Zeitgewinn pro AufgabeBei kleinen Programmen ändert die schnellere Prüfung an Runden und Laufzeit messbar nichts. Ihr Nutzen zeigt sich bei großen Programmen und als Sicherheitsnetz.
  • Beweise mit GrenzenExakt sind sie für Ganzzahlen und Wahrheitswerte. Was Z3 nicht beweisen kann, wird zur Laufzeit geprüft.
  • Junge SpracheGemessen ist QAL an einem Bestellsystem mit zwölf Änderungsstufen. Breitere Erfahrung im Einsatz fehlt noch.
Loslegen

Ein Projekt, ein Speicher, die erste Runde

QAL wird mit Cargo gebaut. Agenten verbinden sich über den MCP-Server; Menschen nutzen dieselben Befehle auf der Kommandozeile.

Bauen

Speicher anlegen und Code schreiben 
qal init && qal define konto.qal
Alle Tests laufen lassen und einen Vertrag beweisen 
qal test && qal prove deposit
Für Agenten: den MCP-Server im Projekt starten 
qal mcp --root .
Ein Programm als Webdienst betreiben 
qal serve handle --listen 127.0.0.1:8080 --allow db
