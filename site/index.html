Eine Programmiersprache für KI-Agenten

Ein Agent schreibt Code und weiß in derselben Runde, ob er stimmt.

In QAL liegt Code nicht in Dateien, sondern als geprüfte Funktionsknoten in einem Speicher. Jeder Schreibvorgang wird sofort getypt, bewiesen, getestet und mit dem Rest des Programms verknüpft. Die Antwort kommt in unter einer halben Sekunde.

  • Verträge (req/ens) werden mit dem Z3-Beweiser bewiesen
  • Jeder betroffene Test läuft mit, auch über Umwege
  • Frühere echte Läufe zeigen, wenn sich Verhalten unbemerkt ändert
Agent → qal_defineQAL
type Acct = { id: Int, balance: Int }

fn deposit(a: Acct, n: Int) -> Acct
  req n >= 1
  ens r.balance > a.balance
= Acct { id: a.id, balance: a.balance + n }

test deposit_adds =
  deposit(Acct { id: 1, balance: 5 }, 3).balance == 8
Speicher → Agent, dieselbe RundeJSON

Der Name

QAL steht für Query & Agent Language

Beide Hälften des Namens beschreiben, wie die Sprache arbeitet.

Q · Query

Code wird abgefragt, nicht durchsucht

Der Code liegt nicht in Dateien, sondern in einem Speicher. Ein Agent fragt ihn ab: wer eine Funktion verwendet (qal_query), wie eine Definition aussieht (qal_view) und wie sie sich verändert hat (qal_history). Jede Antwort ist strukturiertes JSON statt Text, den man erst auswerten muss.

A · Agent

Gebaut für den, der schreibt

Die Sprache ist für KI-Agenten entworfen, nicht für Menschen am Editor. Deshalb prüft jeder Schreibvorgang sofort alles, jeder Fehler hat einen Code, einen Pfad und einen Hinweis zur Behebung, und jede Wirkung nach außen muss ausdrücklich freigegeben werden.

Die eine Runde

Fünf Prüfungen, ein Aufruf

Andere Sprachen verteilen diese Schritte auf Compiler, Testlauf, Linter und Review. In QAL sind sie die Antwort auf jedes Schreiben. Der Agent muss nichts davon selbst anstoßen.

Typen und Effekte

Passt es?

Typprüfung, und jede Funktion nennt, was sie darf: !io, !fs, !net, !db, !model.

Z3-Beweis

Gilt der Vertrag?

Vor- und Nachbedingungen werden bewiesen. Ein widerlegter Vertrag wird gar nicht erst gespeichert.

Tests

Bricht etwas?

Alle Tests, die die Änderung erreichen, auch über andere Funktionen hinweg.

Property-Tests

Und an den Rändern?

Jede reine Funktion bei 0, ±1, leeren Werten und an den Grenzen ihrer Vorbedingung.

Neu verknüpfen

Stimmt der Rest?

Alle abhängigen Funktionen bekommen neue Hashes und werden mitgeprüft.

Dazu kommt das Verhaltensgedächtnis E0807: Frühere echte Programmläufe werden wiederholt, und eine geänderte Ausgabe wird gemeldet.

Was die Sprache kann

Gebaut für den, der den Code schreibt: einen Agenten

Speicher statt Dateien

Code als adressierte Knoten

Jede Definition liegt in .qal/store.db unter ihrem SHA-256-Hash. Umbenennen, Abfragen nach Verwendern und Verlauf sind Speicheroperationen, kein Textsuchen.

Verträge

Beweisen statt hoffen

req und ens stehen an der Funktion. Der eingebettete Z3-Beweiser prüft sie bei jedem Schreiben, und zur Laufzeit gelten sie ebenfalls.

Sandbox

WebAssembly mit Grenzen

Programme laufen in Wasmtime mit festen Grenzen für Rechenzeit und Speicher. Ein Effekt, der nicht freigegeben ist, ist gar nicht verfügbar.

Exakte Ganzzahlen

Keine stillen Überläufe

a * b / c wird mit 128-Bit-Zwischenergebnis exakt gerechnet. Ein echter Überlauf bricht ab, statt falsch weiterzurechnen.

Selbst gehostet

Der Compiler ist in QAL geschrieben

Der Compiler übersetzt sich selbst. Stufe 1, 2 und 3 sind byte-gleich; ein Rust-Referenzcompiler prüft ihn laufend gegen.

std.model

KI-Aufrufe mit Budget

Programme können ein Modell fragen. Jede Antwort wird aufgezeichnet; Tests spielen sie deterministisch und kostenlos ab, ohne Netz.

Ein echter Fang

Alle Tests grün, und trotzdem ein Fehler

Ein Haiku-Agent sollte mehrzeilige Bestellungen einbauen. Nach seinem ersten define bestanden alle seine eigenen Tests. Nur das Verhaltensgedächtnis meldete, dass eine alte, einzeilige Bestellung jetzt anders kostet.

  1. Der Agent las die Warnung und erkannte: Einzeilige Bestellungen müssen gleich bleiben.
  2. Er korrigierte die Rabattformel in der nächsten Runde.
  3. Gegenprobe: Der Stand vor der Korrektur hätte 5 von 50 verborgenen Tests verletzt.

Bei gezielt eingebauten Fehlern meldet E0807 allein, ohne einen einzigen Test, 11 von 13. In 30 Live-Versuchen gab es keinen Fehlalarm.

Warum QAL

Wenn ein Agent den Code schreibt

  • Rückmeldung in einer RundeEin Agent erfährt sofort, ob Typen, Verträge, Tests und Abhängige stimmen. Er muss keinen Build-Lauf planen und keine Logs lesen.
  • Fehler, die Tests nicht sehenBeweise und das Verhaltensgedächtnis fangen, was die eigenen Tests eines Agenten übersehen.
  • Kontrollierte WirkungJeder Effekt steht im Typ und muss freigegeben werden. Ohne --allow model kann ein Programm kein Modell aufrufen und kein Geld ausgeben.
  • Antworten als DatenJedes Ergebnis ist JSON. Jeder Fehler hat einen Code, einen Pfad und einen Hinweis zur Behebung.
Was noch nicht besser ist

Ehrlich gemessen

  • KostenAgenten brauchen in QAL etwa 1,3-mal so viele Tokens wie in Rust. Der größte Posten ist die Sprachreferenz, die jeder Agent mitliest.
  • Kein Zeitgewinn pro AufgabeBei kleinen Programmen ändert die schnellere Prüfung an Runden und Laufzeit messbar nichts. Ihr Nutzen zeigt sich bei großen Programmen und als Sicherheitsnetz.
  • Junge SpracheGemessen ist QAL an einem Bestellsystem mit zwölf Änderungsstufen. Breitere Erfahrung im Einsatz fehlt noch.
Loslegen

Ein Projekt, ein Speicher, die erste Runde

QAL wird mit Cargo gebaut. Agenten sprechen über den MCP-Server qal mcp mit dem Speicher; Menschen nutzen dieselben Befehle auf der Kommandozeile.

Bauen 
cargo build --release --manifest-path qal/Cargo.toml -p qal-cli
Speicher anlegen und Code schreiben 
qal init && qal define konto.qal
Alle Tests laufen lassen und einen Vertrag beweisen 
qal test && qal prove deposit
Für Agenten: den MCP-Server im Projekt starten 
qal mcp --root .
